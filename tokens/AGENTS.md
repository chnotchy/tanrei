# tokens/ — local rules

- Format: DTCG 2025.10. `$type` on groups, object values for `dimension`/`duration`/`color`, aliases in braces. The resolver is `tanrei.resolver.json`; pin `$schema` to `/schemas/2025.10/`.
- Tiers, in reference order: `dial` (the few numbers everything is derived from) < `ref` (raw options) < `sys` (decisions; names are public API) < `comp` (a component's bindings). A token may reference its own tier or a lower one.
- **Every token's value is one of three kinds**: an **alias** (`"{tanrei.sys…}"`, re-pointable); **derived** — a rule in `$extensions["dev.tanrei.derive"]` such as `{ "fn": "mul", "of": "{tanrei.dial.space.unit}", "by": 1.75 }`, written next to the literal `$value` it produces at the dial defaults (the build fails if they disagree); or **fixed** — `{ "fixed": "<why no dial should move this>" }`. A bare literal is rejected.
- **Every token needs a one-product rationale** in `$extensions["dev.tanrei.vocabulary"].rationale`, on the token or inherited from its group: why might *one product* need this distinction? "Material has it" and "Button uses it" are not reasons.
- `vocabulary.lock.json` is generated. If it changes, the vocabulary changed — say so in the PR and the changeset.
- `generated/` is produced from `systems/<id>.system.json` by `@tanrei/token-engine`. Never edit it. To change colors, change that system's palette declarations or role rules (and bump `specVersion` for meaningful role-table changes).
- `systems/` holds design-system layers. A layer changes values; it cannot add token ids except through its `vocabulary` extensions. New vocabulary must pass the one-product test.
- **The root layer (`systems/tanrei.system.json`) sets generated values only**: palettes, color roles, per-state component tokens, and component colors valued by a color rule — what lands in `generated/`. The default system is the documents here as they are written, so every other default is changed in its own document (`dial/`, `ref/`, `sys/`, `comp/`), and a new core token is written there too, with its rationale. A line for such a token under the root layer's `tokens`, or a declaration under its `vocabulary` that is not a color role, would reach every system that extends the root and never the default system: `pnpm validate` and `pnpm generate` refuse it and name the document. Vocabulary extensions (a layer's `vocabulary`, each with a rationale, additive only) belong to the layers above the root.
- `icon-sets/<id>.icon-set.json` holds what an icon set's font cannot tell: the glyph names mirrored in right-to-left, validated by `schema/icon-set.schema.json`. It is data, not a token; a system gets the file whose `families` holds its icon family. The list is regenerated from its `source`, never edited by hand.
- Units are px (= dp = pt = logical px) and ms. Letter spacing is px at the style's own size; emitters convert (em on the web).
- A new component token file must be added to the `comp` set in the resolver, or it does not exist.
- **A group of `comp/` is a component of `specs/inventory.json`, or a set several components read** (such as `comp.input-box`, the box of the text input, the select, the combobox, the number input and the color input). Such a set names its readers (`dev.tanrei.shared.readers`, two or more) and is no component; no reader's own group may repeat one of its names, but those the set lists under `alsoIn` for a part of the reader's own. `validate` holds both (`validateSharedSets`). A value of the set is written once — in the document and in a layer — and a prop bound to one of its axes lists the values its component offers.
- After any edit: `pnpm validate && pnpm generate`, then build the platform packages — the generated Swift/Kotlin/Dart must compile.
