A code block shows code that people read, compare and copy. A name or a command inside a sentence is [Inline code](../inline-code/).

**The code block highlights code by itself.** Give it the code and its `language`, and it colors the code from tokens: no highlighter to install, no theme and no stylesheet to write. So code follows the scheme, the contrast level and the design system like everything else on the page. Highlighting is color and weight and nothing else: the characters, the lines, what is selected, what is copied and what a screen reader reads are the same with it and without it.

### Usage

On the web the code stays in your document, as an ordinary `<pre><code>`. It is there without script: for a reader whose script failed, for search engines, for find-in-page. The element draws the frame around it. Load `@tanrei/web/code.css` to give a block its fill, corners, padding and face before the element is defined.

SwiftUI, Compose, Flutter and React Native are planned: the names beside each platform at the top of this page are the ones the spec gives them, and nothing ships there yet.

`language` is an identifier (`tsx`, `css`, `sh`): it is what the block highlights by, and it is not drawn. The words in the header are `language-label`. A block built by script sets the `code` property instead of holding a `<pre><code>`, and the element writes the `<pre><code>` itself.

**Two looks.** `filled` is a quiet fill, for code on a page. `outlined` has no fill inside one hairline, for code inside a card or a panel that is already filled.

**The body.** A line is never broken by default. A line that does not fit scrolls inside the block, and the page never scrolls sideways. `wrap` breaks lines instead, and a continued row starts under the code, not under the numbers. `max-lines` caps the height in lines, and the rest scrolls inside the block.

**The copy button** is always drawn, never only on hover. It never covers code that cannot be moved clear of it: a scrolling body gains that much room at its end, and wrapped rows stop before its column. It copies the code as plain text, without line numbers, the prompt, the signs or the removed lines. A selection made by hand copies exactly the characters selected.

**Marked lines** are never marked by color alone.

| Mark | Bar at the left edge | Band | Sign | Read before the line |
| --- | --- | --- | --- | --- |
| Highlighted | yes | yes | | `highlighted-label` |
| Added | yes | faint green | + | `added-label` |
| Removed | yes | faint red | − | `removed-label` |

Line lists are numbers and ranges separated by commas (`"3, 7-9"`). They count as the numbers the reader sees, from `start-line`.

**Right to left.** Code is always left to right: lines, numbers and the start of scrolling are at the left in every layout. Only the frame mirrors, so the title moves to the right and the copy button to the left.

### Highlighting

Color comes from one of three sources, in this order.

1. **Runs you give.** Code highlighted where the page was made, or by a highlighter you chose. They are drawn as given, and the block never highlights that code again, whatever `language` and `highlight` say.
2. **The block's own highlighter**, when `highlight` is true, `language` names a language it knows, and the code is no longer than `comp.code-block.syntax.max-length` (50,000 characters).
3. **Plain**, in every other case.

The code is drawn at once, plain. Its colors arrive a moment later, in one frame, and move nothing. Code that changes is read again, and code that grows at its end keeps the colors it has.

| `language` | What happens |
| --- | --- |
| `html`, `xml`, `svg`, `css`, `javascript` (`js`, `mjs`, `cjs`, `jsx`), `typescript` (`ts`, `tsx`), `json` (`jsonc`), `shell` (`sh`, `bash`, `zsh`), `swift`, `kotlin` (`kt`), `dart` | Highlighted. Case does not matter. |
| empty, `text`, `plain`, `plaintext` | Plain. Nothing is reported. |
| anything else | Plain. A debug build reports the unknown language once. |

The block never guesses a language, not from the code, the `title` or the `language-label`. Short code is ambiguous, and a wrong guess colors code wrongly.

**Turning it off.** `highlight="false"` turns the block's own highlighter off for one block. Runs you give are still drawn.

**A limit.** Code longer than `comp.code-block.syntax.max-length` is drawn plain, all of it, never half highlighted. A design system can change the value.

**With added and removed lines**, the block reads the code as the two texts it holds: the code after the change colors the lines that are not removed, and the code before it colors the removed lines. A removed line that opens a string cannot miscolor what follows.

**Failures are quiet.** A highlighter that cannot be loaded, that throws, or whose runs do not join to the code exactly leaves the code plain. The header, the copy button, the lines and the marks keep working.

The grammars are small on purpose. They are meant for showing code, not for editing it. Where a language is hard they can put a run in the wrong color, but they never drop a character.

### Highlighting where the page is made

A site that builds its pages can highlight in the build. The colors are then in the first paint, and the browser loads no highlighter. `highlightToHtml` is the same function the element uses, and it runs in Node.

```js
import { highlightToHtml } from '@tanrei/web/highlight';

const html = await highlightToHtml(source, 'tsx');
// <tanrei-code-block language="tsx"><pre><code data-syntax-of="tsx">${html}</code></pre></tanrei-code-block>
```

`data-syntax-of` on the `<code>` says that the code has been highlighted. The element draws it as given and imports nothing.

### Your own highlighter

`@tanrei/web/highlight` is a module of its own with no dependency. The element imports it the first time a block needs it, and each language's grammar the first time that language is asked for.

| Export | What it does |
| --- | --- |
| `highlight(code, language)` | The runs, or `null` for a language it does not know. A promise the first time a language is used, a value after. |
| `highlightToHtml(code, language, { lines })` | The inner HTML of the `<code>`. With `lines`, one `<span data-line>` per line. |
| `registerLanguage(names, grammar)` | Adds a language or replaces one. A grammar is data: named states, each a list of rules with a pattern, a role and the state to enter or leave. It may be a function that imports the grammar. |
| `loadLanguage(language)` | Loads a grammar ahead of the first code in it. |
| `setHighlighter(fn)` | Replaces the highlighter whole. `null` turns automatic highlighting off for the page. |
| `languages()` | Every name a language is known by. |
| `foldScope(scopes, text)` | The role for a dotted scope name, by the table below. |
| `tokenize(grammar, code)`, `checkGrammar(grammar)` | For testing a grammar you write. |

A product that already has a highlighter it trusts can also set `TanreiCodeBlock.highlighter` to a function `(code, language, signal) => runs`. The block then asks that function, and Tanrei's module is never loaded.

### Syntax roles

| Role (`data-syntax`) | What it is | In the default system |
| --- | --- | --- |
| `comment` | A comment, a documentation comment | Quieter than the code |
| `keyword` | One of the language's own words: a keyword, a modifier, an at-rule, an annotation, an operator written as a word | Purple, one weight step heavier |
| `string` | Text written in the code: a string, a character, a regular expression, the value of a markup attribute | Green |
| `constant` | A value that is not text: a number, a boolean, null, a named constant, a unit, a color value, an escape | Orange |
| `function` | The name of a function or a method, declared or called | Blue |
| `type` | The name of a type: a class, a structure, an interface, a built-in type, a namespace | Blue-green |
| `tag` | What markup and style sheets address: an element's name, a component's name in markup, a selector | Red |
| `property` | A name that belongs to something: a property, a key, a markup attribute, a style property, a command's option | Blue, a tone nearer the code's color |
| `punctuation` | Brackets, separators, the delimiters of markup | Quieter than the code |
| plain (no span) | Anything else: variables, parameters, operators written as signs, text between tags | The code's color |

Each role has two tokens: a color (`comp.code-block.syntax.color.*`) and a weight step (`comp.code-block.syntax.emphasis.*`). The roles are a token axis, so a design system can add one. The default system's green and red come from palettes that are syntax's own, close in hue to the success and error colors. An added or a removed line is told by its bar, its sign and its label, never by color alone. A role changes color and weight only, so highlighted and plain code have the same lines and columns.

A run is a `<span data-syntax="…">` inside the `<code>`. Text outside a span is plain.

### Folding a highlighter's scopes into the roles

Some highlighters name what they find with dotted scope names from one shared vocabulary. `foldScope` folds them into the roles, so that your highlighter and Tanrei's give the same colors. A token's scopes are tried from the most specific outward. Within one scope the first matching row wins. A scope that matches no row is passed over, and a token that matches nothing is plain.

| # | Scope begins with | Role |
| --- | --- | --- |
| 1 | `comment`, `punctuation.definition.comment` | `comment` |
| 2 | `constant.character.escape`, `constant.numeric`, `constant.language`, `constant.other`, `keyword.other.unit`, `support.constant`, `variable.other.constant`, `variable.other.enummember` | `constant` |
| 3 | `string`, `punctuation.definition.string`, `markup.inline.raw`, `markup.raw` | `string` |
| 4 | `entity.name.tag`, `support.class.component`, `meta.selector`, and in style sheets `entity.other.attribute-name` | `tag` |
| 5 | `entity.other.attribute-name`, `support.type.property-name`, `meta.property-name`, `meta.object-literal.key`, `variable.other.property`, `variable.other.object.property`, `support.type.vendored.property-name`, `variable.parameter.option` | `property` |
| 6 | `entity.name.function`, `support.function`, `variable.function`, `meta.function-call.generic` | `function` |
| 7 | `entity.name.type`, `entity.name.class`, `entity.name.namespace`, `entity.other.inherited-class`, `support.type`, `support.class`, `storage.type.primitive`, `storage.type.built-in`, `keyword.type` | `type` |
| 8 | `keyword.operator` whose text is made of letters (`new`, `typeof`, `in`) | `keyword` |
| 9 | `keyword.operator` otherwise | plain |
| 10 | `keyword`, `storage`, `variable.language`, `meta.decorator`, `punctuation.decorator`, `entity.name.function.decorator`, `markup.heading` | `keyword` |
| 11 | `punctuation`, `meta.brace`, `meta.delimiter` | `punctuation` |
| 12 | `variable`, `meta`, `source`, `text`, `markup`, `invalid` | plain |

- A string's quotes are part of the string. An escape inside a string is a constant.
- JSON keys are properties, and their values strings and constants.
- A decorator's name is a keyword.
- `invalid` is plain. A code display does not judge code.
- Added and removed are properties of a line (`added-lines`, `removed-lines`), not of a run.

### What the web draws differently

- The element gives each line a box by wrapping it in `<span data-line>`. It moves your nodes and splits text and runs at line breaks, and adds no character to the code. A framework that owns the children of the `<code>` should pass `code` instead, or render `[data-line]` itself.
- A marked line's label is a hidden `<span>` before the line's code. It is part of the `<code>`'s `textContent`, and is left out of what is copied.
- The outlined look is drawn on whatever it is placed on. Where that is not the surface color, name it in `--tanrei-code-block-ground`, so the line numbers and the copy button can stand on it while code scrolls under them.
- Before the element is defined, `code.css` draws the fill, the corners, the padding and the runs' colors. The header, the copy button, the numbers and the marks need the element.
- `highlight` is true by default, so its attribute is written to turn it off: `highlight="false"`. The property takes a boolean.
- The element writes its own runs as spans into your `<code>`, one line at a time, and marks them as its own. A framework that owns the children of the `<code>` should pass `code` and let the element write them.
- The limit is read from the custom property `--tanrei-comp-code-block-syntax-max-length`, as the cascade gives it to the block.
- A page that uses the single-file bundle has the highlighter inside it. A page that imports `@tanrei/web` as modules loads it on demand.

## Guidelines

### Do

- Give a block that can scroll a `title` or a `label`. The scrolling body is a focus stop and needs a name.
- Use `outlined` inside a card or a panel, and `filled` on a page and on a colored container.
- Use a prompt for a block of commands to type. The prompt is not copied.
- Give every block its `language`. Use `language="text"` for text that has no syntax.
- Put several files or languages in [Tabs](../tabs/) that each hold a code block.

### Don't

- Don't use a code block for a name in a sentence. Use Inline code.
- Don't rely on syntax colors to say something. The same code drawn plain must say the same thing.
- Don't mix commands and their output under one prompt. Every line that is not empty gets the prompt. Use two blocks.

## Accessibility

### What the component handles

- The code is the `code` element inside a group named by `title`, or by `label`.
- A body that can scroll is one stop in the focus order, after the copy button, and scrolls with the arrow keys. A body that fits is not a stop, so a page of short examples adds none.
- Line numbers, signs, bars and the prompt are hidden from assistive technology. A marked line is preceded by its label in words.
- The page never scrolls sideways for a code block, at 320 wide and at twice the text size.
- In forced colors every look gains an edge, all code is the text color, and bars and signs stay.
- Highlighting adds nothing for assistive technology. No role is exposed, and colors that arrive are not announced. The selection, the focus and the scroll position are kept.
- With a red-green color vision deficiency some of the six hues draw together, the green of a string and the red of a tag's name first. Keywords are also told by weight.

### What you need to do

- Provide `copy-label`, `copied-label` and `copy-failed-label` with `copy`, and the label of each mark you use, in your product's language.
- Say in the text around the block what a highlighted line shows. The label only says that it is highlighted.
