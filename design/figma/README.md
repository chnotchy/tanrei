# Figma library

Tanrei's Figma library, "Tanrei Design System", is not public. This page says how it renders the tokens and where it must differ from code, so that a library built from `design/tokens/` can follow the same conventions.

The file is a rendering of `tokens/` and `specs/`. It was built through the Figma MCP server from the resolved tokens in `design/tokens/`, so no value in it was typed by hand. See [`../README.md`](../README.md) for why design tools are never the source of truth.

Every component page follows Button's: a documentation frame (properties, use, states, source), the component set on a surface panel, the four mode panels, and the spec's fixtures drawn as instances. Every fill, stroke, radius, size, padding, gap and opacity binds the `tanrei/comp` / `tanrei/comp.color` variable of its axis value and state; every text uses a `tanrei/typescale` style.

Every variable has a scope (none use `ALL_SCOPES`) and WEB code syntax equal to the real CSS custom property, e.g. `var(--tanrei-sys-color-primary)`.

## Where Figma differs from code (by necessity)

| Difference | Reason |
|---|---|
| Four color modes, not six — medium contrast is code-only | Professional plan allows 4 modes per collection |
| State opacities are stored as percent (8, 10, 12, 16, 38) | Figma reads a number bound to layer opacity as 0–100; each variable's description gives the code value |
| Token weights 450 / 550 are exact | Figma ships Inter as a variable font; the six affected text styles set `wght` through `fontName.variationSettings` (the style name still reads Regular / Medium) |
| Choices of kind are not drawn | `sys.behavior.*` (ripple, glow) are behaviour; the file draws every state with the default choices. Corner smoothing IS drawn: every Button variant's `cornerSmoothing` is the system's `sys.shape.corner-smoothing` (0 in `tanrei`, 0.6 in `cupertino`). The touch target (48, `sys.target.touch`) is a hidden frame in every variant: turn on `Show touch target` |
| State colors are stored results, not rules | Figma variables cannot mix two colors. The sync writes what the system's rule yields in each mode; code computes it live |
| Derived values do not follow the dials inside Figma | Variables cannot multiply. Change a dial in the layer file, run `pnpm generate`, re-sync |
| "Clip content" is on only where a shadow or the content needs it | Figma only renders a shadow's spread — the 1px elevation ring — on clipped frames, so the contained Loading indicator and every Card's `Container` clip. A control's own frame (Button, Icon button, the selection controls, Text field) does not: its focus ring and touch target draw outside it. A Card clips an inner `Container` and draws the focus ring on the unclipped frame around it; the FABs do the same. A Chip draws its container — fill, outline, elevation — on a clipped `Surface` placed behind an unclipped content row, so the remove action's focus ring, which reaches the small chip's edge, is not cut. A list item, a menu item and a tab draw their focus ring inside their own edge, as code does (LST-4, MNU-11, TAB-4); the inner ring's corner is the item's shape less the outer width, computed when the file is built. A snackbar draws its fill, corners and `level3` on a clipped `Surface` behind an unclipped bar, as a Chip does, so a control's focus ring, which reaches past the bar's edge, is not cut. A rich tooltip and a dialog clip their own frame: nothing in them draws outside it. The app bar does not clip, so its buttons' focus rings are not cut; a navigation bar's, rail's or drawer's destination draws its ring outside its item container, as code does, and the bar and the rail do not clip. A drawer clips its frame, which rounds a modal drawer's end corners and draws `level2`'s ring. A segment does not clip: its focus ring is inside its edge (SEG-5) and its touch target reaches past it. The FAB menu's toggle is drawn as the FAB, and an item as a chip, its fill, corners and `level2` on a clipped `Surface` behind an unclipped row. A button group's and a split button's halves are Button instances, which do not clip, so an elevated split button draws no `level2` ring (99 × 36 against the web's 101 × 38, ring included) A toolbar draws its fill, corners, outline and elevation on a clipped `Surface` stretched behind its unclipped items, as a snackbar does, so an item's focus ring is not cut; a docked toolbar's `Surface` strokes only its top edge. A slider and its handle do not clip: the value indicator draws above the slider. The search bar does not clip; the docked search view clips to its corners and draws `level2`'s ring. A bottom sheet and a side sheet clip their frame, which rounds their corners, cuts the content at a detent's height and draws `level2`'s ring (the drag handle's focus ring and the close button's lie inside it). A carousel clips its row at its edges, where the items scroll under its padding, and each item clips its content to its corners, so an item draws its focus ring inside its edge, as code does (CRL-3). A date picker and a time picker clip their container, which rounds it and draws its elevation's ring; the rows inside them do not clip (an auto layout the file creates clips by default, and theirs was turned off), so a text field's floated label and a focus ring are not cut |
| Big matrices are split the Figma way | Icon button's 180 drawings are two sets — `Icon button` (60) and `Icon button / Toggle` (120). A selected toggle draws the filled glyph (FILL 1), a different icon component, so its glyph has its own swap property, `Icon (selected)`; one swap value cannot serve both selections. Chip's 180 are split by kind — `Chip / Action` (40), `Chip / Filter` (80), `Chip / Input` (60) — and Extended FAB's 135 by form — `Extended FAB` (90) and `Extended FAB / Collapsed` (45), because a collapsed button is a different drawing (a square without its label), not a property of the expanded one |
| Some booleans are variants | A boolean cannot change a size or a padding. Switch's `Icon` is a variant because the handle grows to `switch.handle.size-with-icon` (the larger of the two in tanrei; a system whose condition size is larger must be re-bound). Text field's `Value` is a variant because the label moves between resting and floated. Card's `Inset` is a variant because it removes the padding. Extended FAB's `With icon` and Chip's `Leading` are variants because a glyph or an avatar changes the start padding (`padding-inline-start-with-icon`, `padding-inline-with-icon`, `padding-inline-with-avatar`); a selected filter chip draws the check whatever its `Leading`, so turning `Selected` off brings its icon back. List item's `Lines` is a variant because each line count has its own minimum height (48 / 64 / 80) and three lines align the row's ends with the top of the text; Tab's `Content` because a primary tab that stacks its icon above its label is 64 high. Snackbar's `Controls` is a variant because a control changes the bar's end padding (`padding-inline-end` 16, `padding-inline-end-with-controls` 8) and its `Layout` because the action moves to its own row; Dialog's `With icon` because the icon centres the headline. App bar's `Navigation` is a variant because without a navigation button the title starts `title.inset` 16 from the edge rather than after `container.padding-inline` 8 (APB-4), and its `Size` and `Scrolled` because an expanded large bar has a row of its own; without actions its title still ends `padding-inline` 8 from the end rather than `title.inset` 16, which only moves where a long title is cut. List item's `Type` and Menu item's `Kind` are variants because a static item, an action and an option draw different parts and states; the matrices are sparse where the spec is (a static item has no states, only an option is selected, only an action is destructive). A segment's `Label hidden` is a variant because an icon-only segment keeps its icon when selected and draws no check; its `Show icon` is a boolean, since the icon changes no padding. Button group's `Count` is a variant because the last item keeps its own end corners in a connected group; Split button's `Open` because the trailing half's inner corners change, and FAB menu's `Open` because the open toggle has its own colors, corner and glyph (a disabled FAB menu is drawn closed, so `Open` True has no Disabled: 81 variants). A split button's `Show icon` on the leading half cannot change its start padding to `leading.padding-inline-start-with-icon`: the fixture `filled-icon` binds it on the instance (the two are equal in tanrei) Search's `Leading` and `Trailing` are variants because a slot button changes the bar's start or end padding (`padding-inline` 12 or `padding-inline-with-button` 4), and its `Value` because the clear button — shown with a value, hidden while disabled — ends the bar `padding-inline-with-button` from its edge. Toolbar's `Orientation` is a variant because the paddings and the minimum size change axis (a docked toolbar is always horizontal, so it has no Vertical). Bottom sheet's `Handle` is a variant because without the handle's row the content is padded from the top too, and its `Inset` because it removes the content's padding; Side sheet's `Header` and `Actions` because without them `container.padding-block` pads the content from the top or the bottom. Carousel's `Layout` is a variant because each layout places its slots differently (the widths are computed when the file is built). Date picker's `Entry` and `View` are variants because the fields or the years replace the calendar's rows, and its `Presentation` because a docked picker draws no header and no actions; a day's `Range start` and `Range end` are conditions of their own because they add the half-cell band. Time picker's `Clock`, `Unit` and `Layout` are variants because the period, the dial's numbers and the arrangement change; the period's place (before the hour in ja, TMP-10) is two booleans, `Show period before` and `Show period after`, because an instance cannot reorder its layers |
| A label is centered on the control's first line by a derived offset | Figma has no first-line alignment. Checkbox and Radio button lower the label by (container.size − the body line height) / 2 = 3; Switch lowers the track by (22 − 20) / 2 = 1. Derived from two values, not a token. A snackbar's controls sit in a row as tall as the message's body line (22) and overhang it into the padding, so they stay centred on the first line (SNK-15) however many lines the message has. To wrap a label, set the instance's label to Fill and resize the instance |
| Checkbox's mark is a vector | Square caps, miter join, stroked at `checkbox.mark.width` through (0.2, 0.5), (0.4, 0.7), (0.8, 0.3) of the box's side; the dash from (0.1375, 0.5) to (0.8625, 0.5). The box's fill is an inner frame inset by the outline width so a translucent fill never sits under the outline; its corners reuse `checkbox.box.shape` (code insets the radius by the outline width) |
| Rings and arcs are vectors on a bound stroke | Progress and Loading indicators draw their arcs as vector paths whose stroke weight and color are bound; the path's radius is computed from the size and thickness when the file is built |
| Progress indicator's stop indicator is hidden | It is bound to `progress-indicator.stop-indicator.size`, which is 0 in tanrei; Figma cannot draw a 0-size node, so it hides behind `Show stop indicator` for a system that sets a size |
| Motion is one frame | Indeterminate progress shows a segment of the bar and a quarter of the ring, the loading indicator a quarter arc; a focused text field shows its caret (`border.hairline` wide). Durations stay variables only; a focused search bar and the full-screen header show theirs, before the placeholder or after the value |
| Positions are not variables | A badge sits on its anchor by `badge.dot.offset` / `badge.container.offset` (a navigation bar's or rail's destination places its dot and count badges on the icon's top-end corner inside its item container) and an outlined text field's notch by its padding; Figma cannot bind x or y, so the fixtures are placed by those values when the file is built. A time picker's dial numbers, handle and track sit at the angles and radii TMP-12 and TMP-13 give, computed when the file is built |
| An outlined text field's notch is a surface-colored patch | Figma cannot open a gap in a stroke, so the floated label sits on a `surface` notch padded by `text-field.outline.notch-padding` on each side; the field reads right on surface. The input line is as tall as the input style's line (22 / 26) and a resting filled field keeps half the floated line (8) above and below it, so its label rests centred and the box keeps its height — Figma cannot bind a size to a text style. Showing an icon keeps `container.padding-inline` rather than `padding-inline-with-icon` (a boolean cannot change a padding): 4 px wider at the icon's side than code. A field has no Pressed state and no focus ring (TXF-7) |
| Card content is a stand-in | `Title` and `Body` stand for the product's own content in the variant's content color; the flush card's media placeholder is `surface-variant` |
| An input chip's avatar is a stand-in | The avatar is an image in code; the file draws an `outline`-colored circle of `chip.avatar.size`, clipped to `chip.avatar.shape` (`surface-variant` would vanish into a hovered or selected container). Disabled, it is drawn at `sys.state.disabled-content-opacity`, as code does |
| Elevation per state is an effect style, picked when the file is built | A shadow cannot be a variable. Each state's elevation token resolves to one of the six `tanrei/elevation/levelN` styles, and that style is set on the variant (FAB and Extended FAB: level3, level4 hovered, level0 disabled; elevated Chip: level2, level3 hovered, level0 disabled; plain Tooltip level0, rich Tooltip level2, Snackbar and Dialog level3; App bar, the navigation bar and rail and a standard drawer level0, a modal drawer level2; the FAB menu's toggle level3, level4 hovered, level0 disabled, open or closed, and its items level2; an elevated split button level2, the Button's own; a segment level0 in every condition and state, so it sets none; a floating toolbar level3 and a docked one level0; the docked search view level2; the search bar and a slider's handle level0, so they set none; a bottom sheet level2 in both variants, a standard side sheet level0 and a modal one level2; a carousel draws none; a modal date picker and the time picker level3, a docked date picker level2). A system whose rule yields other levels must be rebuilt |
| A part with its own states is its own component | An input chip's remove action has its own hover, focus and press (CHP-20) while the chip keeps its state, so it is `Chip / Remove`, nested in every `Chip / Input` variant as an exposed instance: set its `State` on the instance. It sits centered on a glyph-sized slot (`chip.icon.size`), overhanging it by (remove size − icon size) / 2 as in code; positions are not variables. The snackbar's action and close button answer their own states while the bar answers none (SNK-2), so they are `Snackbar / Control`, nested as exposed instances in every `Snackbar` variant; a dialog's actions are exposed `Button` instances. A split button's halves each answer their own states (SPB-4), and a button group's items are Buttons and Icon buttons (BGR-5), so both are exposed `Button` / `Icon button` instances: set each one's `State` on it. A FAB menu's items answer their own states while the toggle answers its own, so an item is its own component, `FAB menu / Item` A slider's handle answers its own state while a range's other handle keeps its own (SLD-11), so it is `Slider / Handle`, nested in every `Slider` variant as an exposed instance. A toolbar's items are exposed `Icon button` instances, and a search bar's slot and clear buttons and the full-screen header's back and clear buttons too. A bottom sheet's drag handle answers its own states while the sheet answers none (BSH-13), so it is `Bottom sheet / Drag handle`, nested as an exposed instance; a side sheet's close button and actions are exposed `Icon button` and `Button` instances, and a carousel's items exposed `Carousel / Item` instances. A date picker's days, years and view toggle, and a time picker's selectors and period segments, answer their own states while the picker answers none, so each is its own component (`Date picker / Day`, `Date picker / Year`, `Date picker / View toggle`, `Time picker / Selector`, `Time picker / Period segment`) nested as instances; their month buttons, entry-mode toggles, fields and actions are exposed `Icon button`, `Text field` and `Button` instances |
| A row of items is a frame, not a component | Figma cannot add children to an instance, so the element that holds a component's items is drawn in the fixtures as a frame, not offered as a component. A list draws nothing, so it is `List item` instances stacked without a gap. A menu's surface is a frame bound to `comp.menu.surface` (color, shape, padding, `min-width` 160 and `max-width` 320), raised by `tanrei/elevation/level2` and clipped, holding `Menu item`, `Menu group title` and `Menu divider` instances at Fill. A tab row is a frame 360 wide holding `Tab` instances — at Fill for a fixed row, at Hug and clipped for a scrollable one — over a divider frame bound to `comp.tabs.divider`. A navigation bar is a frame 360 wide and at least `container.height` 64, its destinations at Fill (equal cells) and centred in its height, under an outline frame along its top: the cell, the hit area, is not drawn. A navigation rail is a frame `container.width` 80 wide and as tall as the harness's stage (400), its header — an `Icon button` instance — `container.padding-block` below its top, the destinations `header.gap` below it at Fill, `container.gap` apart, and an outline frame along its end. A navigation drawer is a frame `container.width` 280 wide (560, or 640 for the modal one), padded by `container.padding-inline` and `container.padding-block`, holding `Navigation drawer / Heading`, `Navigation drawer / Destination` and `Divider` instances at Fill `container.gap` apart, its end corners bound to its variant's shape; the modal fixture lays it on a 480 × 640 window filled with `surface` under `navigation-drawer.scrim.color`. A segmented button is a frame filled with `set.color`, padded by `set.padding` and cornered by `set.shape`, holding `Segmented button / Segment` instances with a `divider.width` frame of `divider.color` between each two, at Fill height; every segment is given the widest one's width measured as if selected (SEG-14), computed when the file is built; the first segment's start corners and the last one's end corners are bound to `set.shape` on the instance (`set.shape` − `set.padding`: `set.padding` is 0 in tanrei; a system with a padding must bind the computed value); the outline is an absolute `Outline` frame over the segments, because a frame's own stroke draws under its children and a selected segment's fill would cover it. An open FAB menu is the harness's 320 × 320 stage, the toggle 16 from its end and bottom edges, under it a column of `FAB menu / Item` instances `list.offset` 8 above the toggle, `list.gap` 8 apart and end-aligned with it. A button group is a component, not a frame, because its items are components already and the group only spaces them and sets their inner corners A toolbar is a component, not a frame, because its items are components already and it only spaces them (as a button group). A search's docked view is a frame filled with `view.container.color`, cornered by `view.container.shape`, padded by `view.padding-block` and `view.padding-inline`, raised by `level2` and clipped, holding `Search / Suggestion` instances at Fill, `view.offset` 4 below the bar in the harness's 360 × 320 stage padded 16; the full-screen view is the 360 × 480 window filled with `view.container.color`: a `Search / Header` instance at Fill over a frame padded as the view, holding the suggestions |
| A menu item has no Fill layer, so a surface hugs its widest item | Figma sizes a hugging frame from children at Fill only one level deep, so a menu item is two groups set apart by space-between: its start (mark, leading icon, label and supporting text) and its end (trailing text and icon). An auto layout whose children are all hidden keeps its last size, so the end has its own boolean, `Show trailing`, with `Show trailing text` and `Show trailing icon` inside it. Labels are auto width: a menu label does not wrap at the surface's 320, and a fixed tab too narrow for its label overflows instead of growing (TAB-14); give a longer label a fixed width |
| A list item's divider is a sibling of its row | Code dims a disabled item and never its divider (LST-22), and a layer's opacity reaches everything inside it, so an item is a column holding the `Row` (container, colors, opacity) and an absolute `Divider` along its bottom. The divider starts at the text column through spacers bound to the leading icon's, avatar's and image's sizes and to the same booleans, so it follows the leading element |
| An overlay's surroundings are drawn by its fixtures | A tooltip's anchor, a dialog's scrim and window, and a snackbar's host are not part of the component. The tooltip fixtures are the web harness's 320 × 200 stage with a medium standard `Icon button` at its centre and the tooltip placed `tooltip.offset` from it (flipped below for `plain-bottom`, kept `window-margin` inside); the dialog fixtures are 480 × 640 windows filled with `surface` and `dialog.scrim.color` over it, padded by `dialog.container.margin`, the dialog centred; a snackbar is drawn in place, centred on a 400 wide stage (SNK-19). The bottom sheet fixtures are the harness's 400 × 720 window, filled with `surface` and, for a modal sheet, `bottom-sheet.scrim.color` over it, the sheet at its bottom edge; the side sheet fixtures the 720 × 480 window, the sheet at its end edge, a modal one over `side-sheet.scrim.color`. The date picker fixtures are the harness's 480 × 640 window under `date-picker.modal.scrim.color` for a modal picker, the picker centred, and a 400 × 440 stage for a docked one, the picker 20 from its start and top (its anchor is not drawn); the time picker fixtures a 480 × 640 window (horizontal: 720 × 480) under `time-picker.scrim.color`, the picker centred. Placement, opening, dragging and motion are not drawn |
| A text wraps only in an instance of fixed width | Tooltip, snackbar and dialog texts are auto width, so a component hugs its content between its bound min- and max-width; auto layout does not wrap an auto-width text at a max-width, and resizing a text inside an instance does not stick. To wrap one, set that text to Fill and give the instance a fixed width — the fixtures use the width the baseline's window leaves (plain-wrapped 200, rich-untitled 304, the snackbar's 368, the dialog's 448) |
| A scrolling dialog is an instance of fixed height | The supporting text and the content are one `Body` group (`Show body` hides both, since an auto layout whose children are all hidden keeps its size). For a dialog taller than its window, set the instance to a fixed height (Fill in the window) and the `Body` to Fill: it clips the text. The dividers are absolute frames across the container, pinned to the top of the body and to the top of the actions, shown by `Show top divider` / `Show bottom divider` as DLG-11 would at that scroll position; their positions are computed when the file is built |
| One text property has one value in every variant | A `TEXT` property is shared by the variants it is linked in, so a rich tooltip's default text is the plain one's (`Move to trash`), and a range date picker's `Label` is the single one's (`Select date`: the range fixtures set `Select dates`); set it on the instance |
| The navigation bar's and rail's destinations are two components | They share a structure and are built by one script, but each binds its own component's tokens, which a design system may set apart — m3-like's bar item container is 64 wide against the rail's 56, cupertino's bar `item.gap` is 2 against the rail's 4 — and the rail's label takes two lines where the bar's takes one. One component would bind one of them for both |
| A rail destination's minimum height is derived | NVR-6 makes a cell at least `sys.target.touch` 48 with half of `container.gap` above and below the destination. The rail frame binds `container.gap` between destinations, so a destination is at least 48 − 8 = 40, computed when the file is built: a rail without labels puts its item containers 48 apart, as code does |
| A large app bar spreads its two rows apart | A Fill child does not grow a hugging parent, so an expanded large bar is at least `container.height.large` 112 with its top row and its title block both hugging, set apart by space-between: the block ends `container.padding-block-end` above the bottom edge, and a subtitle grows the bar to 130, as in code. Collapsing is not drawn (`Scrolled` True is the collapsed bar). A centred title is a block across the whole top row with its text centred on the bar; code narrows it to clear the navigation and action slots (APB-6), the file does not: shorten a title that would reach them |
| A navigation bar's label does not truncate | A bar destination hugs its content and the bar gives it an equal cell, so its label is auto width and a label longer than the cell overflows instead of ending in an ellipsis (NVB-12); give a long label a fixed width. The rail's label wraps in the rail's width and is cut after two lines, as code does |
| A drawer row with a wrapped label stays 44 until its text is taller | The label fills the row and wraps; the row is at least `item.container.height` and grows only when the text is taller than it, as Compose and SwiftUI draw it (the web adds a line per extra line). A destination's default width is the drawer's inner width, 280 − 2 × 12 = 256, computed when the file is built; the fixtures set it to Fill |
| A split button's halves are Button instances rebound by overrides | The halves are drawn by `Button`, not redrawn, with every padding, gap, height, corner, icon-size and outline-width binding and every color overridden to the split button's variable of its variant and state. Figma keeps an instance's override through a change of its variant only where the two variants agree: the geometry bindings stay when a half's `State` changes, but the color bindings go back to Button's for the new state (and return on going back to Enabled). The set draws both halves Enabled and the disabled fixtures rebind the Disabled colors; after any other change of `State` a half shows Button's color for that state, which has the same value as the split button's in all four modes of every design system's plan (tanrei, m3-like, m3-expressive-like, cupertino). A half's focus ring is the Button's and keeps the Button's corners where the halves meet |
| Joined items take their inner corners from the instance | A connected button group's items and a segmented button's end segments differ from their component only in some corners, so those corners are bound on the instance — `button-group.connected.inner-shape` on every corner that faces a neighbour, `segmented-button.set.shape` on the set's outer corners — and stay through a change of the item's `Variant`, `Size` or `State`. A connected icon button is `sys.target.pointer` 44 wide around its glyph (BGR-3), the width the web draws for a fine pointer; code gives touch input `sys.target.touch` 48. The items are centred in the row, not stretched to the tallest (BGR-1): give every item of a group the same size. The focus ring of a focused item keeps the item's own corners |
| A slider's value is drawn by the file, not set on an instance | Figma refuses to move a layer inside an instance and ignores a size override on one, so a value cannot be an instance property. `Slider` draws value 40 of 0–100 in every variant — the handle's centre at `container.size` / 2 + thickness / 2 + 0.4 × the handle's travel (131.6 small) — and the fixtures whose value is 40 (continuous, value-indicator, medium, large, disabled) are its instances; discrete-stops, range, centered, vertical and disabled-stops are frames that draw the track, the active track and the stop dots, bound as the component's, around `Slider / Handle` instances, their positions computed from the value when the file is built. Resizing a `Slider` instance stretches its track and keeps the end dot at the end, but leaves the handle and the active track where they are |
| A docked toolbar spreads its items with Space frames | Figma's space-between puts a lone item at the start and has no minimum gap, so the docked toolbar centres its items with a `Space` frame at Fill between each two, at least `container.gap.docked` 8 wide (TBR-2's minimum), hidden with the item after it (`Show item n`): one item leaves no space and is centred. The system inset is not drawn (TBR-3) and the row does not scroll (TBR-8): an item that does not fit overflows |
| A sheet's height is an instance's fixed height | A bottom sheet hugs its content up to its detent; Figma cannot take a fraction of a parent, so a detent is drawn by giving the instance a fixed height — `container.partial-fraction` 0.5 of the area (360 in the 720 window) or the area less `container.margin-block-start` 48 (672) — and setting its `Content` to Fill, which clips the text, as a scrolling dialog does. A side sheet is 480 high, the harness's window, and takes its parent's height at Fill |
| A carousel's slots are computed when the file is built | Figma has no arithmetic, so each `Layout` variant places its items at the widths the previous revision's CRL-10, CRL-11 and CRL-13 gave for the harness's 400 wide row and the default `container.large-width` (not rounded: 101.33 and 50.67); a carousel at another width or with another `itemWidth` must be recomputed. A size override on a nested item does not stick, so the previous revision's narrow-items fixture (itemWidth 120: 120, 120, 64, 40) is a frame bound as the component, holding `Carousel / Item` instances. Scrolling, which moves and resizes the items (CRL-12), is not drawn |
| A carousel item's state is a layer over its content | An item's content is usually an image that covers its container, so code draws hover, focus and press as a state layer over the content (CRL-16) and keeps the container at its resting color; the file does the same — a `State layer` frame in `item.<state>.state-layer.color` at the `sys.state` opacity, not the stored `item.<state>.container.color` mix, which only shows where the content leaves the container uncovered |
| A calendar is 42 day instances, set per month | Figma cannot generate items, so a `Date picker` variant holds 42 `Date picker / Day` instances — six weeks of seven, Sunday first — drawn for September 2026; another month, first day of the week or choice is drawn by setting each cell's `Label`, `Show day`, `Condition` and `State` and the weekday names on the instance, as the fixtures `docked-monday` and `docked-unavailable` do. The year view holds 21 years (2020 to 2040); the list's scrolling is not drawn. A range's band is the in-range days' containers across their cells and a half cell (24, computed) beside the start and the end, toward each other |
| A date picker is 360 wide, computed | A year view and a typed picker have no row as wide as the grid, and a width cannot be a sum of variables, so every `Date picker` variant is 7 × `cell.size` + 2 × `container.padding-inline` = 360 wide, fixed, with its rows at Fill, and a year is a third of the grid (112). A system with another cell size or padding must be rebuilt. ## How the file is synced

`node packages/tokens-build/src/cli.js figma-plans <dir>` writes one **sync plan per design system** to `<dir>/<id>.json` (`tanrei.json`, `m3-like.json`, `m3-expressive-like.json`, `cupertino.json`): every collection, variable, scope, WEB code syntax, value or alias per mode, plus text and effect styles. The plan is generated from the same resolved model as every platform's code, so nothing in Figma is typed by hand. It is not part of `pnpm generate`, and the repository holds none: a plan is of use only to whoever applies it to a Figma file.

The plan is applied through the Figma MCP server **by variable name, in place** — never delete and recreate a variable, or every binding in the file and in consumers' files breaks. When the vocabulary renames a token, record it in [`renames.json`](renames.json) first so the sync renames instead of recreating. Variables that leave the vocabulary are deleted only after no node binds them.

After a sync, verify rather than trust: the same digest (names, scopes, code syntax, values per mode) is computed over the plan and over the file, per collection, and must match. Figma stores a description HTML-escaped (`'` comes back as `&#39;`): decode before comparing. Figma rounds line heights and letter spacing to 0.01 px (body 22 against 21.9996); colors are stored at the plan's four decimals, not as n/255.

1. Change `tokens/` or `specs/`, then `pnpm generate`, then write the plans (`figma-plans <dir>`).
2. Apply `<dir>/<system>.json` to that system's file and compare digests.
3. Review the four mode panels on the Color and Button pages, then publish the library with a note that names the token change.

One file per design system: this file is `tanrei`. The presets' plans are written the same way; their files are not built yet.

Never correct a value in Figma first. It will be overwritten, and the five code platforms will not follow.

## Pages, cover and logo

- **Cover** is 1440 × 900. Figma's Community thumbnail crops to 2:1, so the outer 90 px top and bottom may be cut there. It carries no legal text: the license, the Material Design 3 methodology statement, the trademark note and the fonts' licenses are content — the **Legal** section at the bottom of *Getting started*, a summary of the repository's `NOTICE` and the documentation's License page, which are the source.
- **Logo** holds two components, `Logo / Symbol` (the T) and `Logo / Wordmark` (“Tanrei” in Shippori Mincho), both bound to `on-surface` so they follow the mode. One at a time, never together: the symbol where the name is not read (thumbnail, icon, page header), the wordmark where it is (cover, page title). The rules are on the page. The “端麗” characters on the cover are an ornament, not a mark.
- **Foundations / Color** lays light and dark side by side and the high-contrast pair beneath them, so the same swatch can be compared across modes at a glance. Intents read primary, secondary, info, success, warning, error, then the palettes a design system declares (accent) — new palettes append below. Medium contrast exists in code only (four modes per collection on this plan).
