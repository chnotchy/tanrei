# specs/ — local rules

- One file per component: `<name>.spec.json`, validated by `component.schema.json`. `name` equals the file name and must be listed in `inventory.json`.
- **"Input", "field" and "Field" in a name**: a component named "… input" is a base control a person types into, with no label row and no message of its own (the one-time-code input). A component named "… field" is a composed component — the Field's frame and the one control it frames — complete by itself: its props are its members', marked `from`, and its sentences cite theirs (the one-time-code field: `builtFrom` field and one-time-code-input). "Field" alone is the frame. No other component draws the frame itself: a text field, a number field and a color field are each a Field around their input, and a select and a combobox are bare controls that kept their names, with a select field and a combobox field around them.
- **`level`, `builtFrom` and `uses`**: every spec says which of the three levels its component is of, and `inventory.json` says the same. `base`: a single part with one job, built from no other component. `composed`: components put together to complete one value or one job. `feature`: several controls, each with a value or an action of its own, coordinated by state the component itself holds. A component of any level may have parts of its own. `listing` says whether it is listed by default (`default`) or only when a reader asks for everything (`advanced`: a base component that is a member of at least one `default` one), in the spec and in `inventory.json` alike. `builtFrom` names its **members** — each component that holds its value, does the one job it exists for, or frames it — and is left out at `base`, required at `composed`. `uses` names every other component it is built with: one it brings for a small part (a stepper is a Button, a requirement mark a Tag), and one the product places in it that it only lays out (each other `items[].component`, a component a slot is for). Neither changes the level. `validate` holds what a field can say (`packages/tools/src/levels.js`).
- **`from`, `fills` and `twin`**: a prop, an event or a slot of a composed component that is a member's is written `{ "name", "from": "<member>.<name>" }` and nothing else but a `note` — it is written once, in the member's spec, and read resolved (`packages/tools/src/from.js`). An item kind as a whole may be a member's too (`{ "name", "from": "<member>.<kind>" }` in `items`: a select field's options are its select's) — forwarded whole or written whole, never prop by prop — and a fixture item of a kind that is another component may hold that component's `items` and fill its `slots`. A member's prop the component sets itself is named in `fills`. Where a composed component forwards props and has no part of its own, every fixture names its `twin`, the member's fixture that is the same thing made by hand; `validate` holds that the two set the same values. `platforms.<p>.props` and `.events` are still written in full.
- Behavior is EARS (`WHEN/WHILE/IF/WHERE … THE <component> SHALL …`) with stable ids. Never renumber; retire an id by deleting it and never reuse it.
- `fixtures` are the shared visual contract: every implemented platform snapshots every fixture under the same id. Cover each variant, size and non-default state.
- `platforms.<p>.props` maps **every** spec prop to that platform's idiomatic name; `events` likewise. Inverse flags (`enabled`) and sentinel idioms (null callback) are fine — say so in `notes`.
- `status` is a claim the parity check verifies. Only raise it after implementation, tests (citing behavior ids), baselines and docs exist. Lower it if they stop existing.
- New components and breaking changes start as a proposal, reviewed before it changes anything here.
